Decoy Canary Wallet

One real payment hides among decoys. If a decoy moves when you did not move it, the wallet enters a protected state and stays there until both parties authorize.

Simulation: mock keys, no real network, no real Zcash

Decoy Watcher: a separate page that watches real decoy addresses on Zcash testnet.

Try it in four steps
  1. Press Alice + Bob pay. It works because both parties authorize.
  2. Press New wallet, then Thief sweeps what the stolen key can spend. The thief takes the decoys, the alarm fires, the real output stays safe.
  3. Try Alice + Bob pay: blocked. Try Unlock: Alice only: rejected. Try Unlock: Alice + Bob: back to normal.
  4. New wallet, sweep again, then Mine +10 blocks and Release with recovery key (the fallback if the receiver disappears).

Outputs

    Play

    Payment

    The network fee is taken out of the amount you send, so Bob receives the amount minus the fee. Leave it empty to send the whole real note. Anything left comes back to Alice as change.

    Attacker

    The thief holds Alice's stolen key only, not Bob's.

    Recovery

    Setup

    Decoy value: leave empty for automatic (0.1% of the real note, never below 10 times the fee), or set your own. It must be above the fee, or sweep tools skip the decoy and the alarm never fires.

    Event log

      Protect a payment: plan the decoys

      Type the amount you want to send. The network fee comes out of it, so the receiver gets a little less. Set your own decoy value, or leave it on auto, and see how many decoys to make and what they cost. This only plans. It does not send money or connect to a wallet. Amounts are in ZEC; the default fee is the one measured on Zcash testnet.

        Attack odds

        A model, not a guarantee: it assumes the attacker cannot tell the outputs apart and touches them in random order. Against a thief who sweeps everything, what protects the real funds is the two-party rule, not the odds.

        Honest limits

        • This is a simulation. Keys are mock strings. There is no real cryptography and no connection to Zcash.
        • The protected state is client-side. It stops this wallet from signing. It does not stop someone who holds the keys from spending on the ledger. The decoys are the alarm; the two-party rule protects the real funds.
        • Bait costs real value. Decoys hold a small amount (0.1% of the payment, above the fee) that outsiders cannot see. A thief holding the key can read amounts, and keeps any decoy they sweep.
        • Attackers who control the wallet can learn which output is real, and then the decoys no longer help.
        • The recovery key is a single point of trust. Once the timelock opens it works even while the wallet is protected, because it is the way out if the receiver disappears. Keep it separate from everyday keys. The timeout is a trade-off between weaker protection and stuck funds.
        • The alarm is early warning, not prevention. By then a decoy is already gone. The two-party rule on the real output is what protects the real funds.
        • The shielded model is simulated. Hidden amounts only means the outsider view leaves them out; there are no real commitments or proofs. As far as we know a shielded note cannot carry a timelock, so a real version would use a third key share. To be checked on testnet.
